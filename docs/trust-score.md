# AgriTrust-5D · 溯源可信度评分模型

> 面向毕业设计的算法说明，配套实现：`backend/src/main/java/com/agri/trace/service/TrustScoreService.java`
> 前端展示：`components/business/trust-score.vue`（移动端）、`pages-pc/batch/detail.vue`（PC）

## 1. 要解决的问题

现有农产品溯源系统普遍只回答一个问题：**"这条记录上链了吗？"**

这是一个二值判断，且存在两个明显缺陷：

1. **不可量化**——上链了就是"可信"，没上链就是"不可信"，中间的灰色地带完全丢失。一份只有种植记录、缺质检和物流的档案，和一份全流程齐全的档案，在系统里没有区别。
2. **不可解释**——即便系统给了个"可信"标签，消费者也无从知道依据是什么，标签本身退化成装饰。

AgriTrust-5D 把可信度拆成五个**可观测**维度，分别计分后加权求和，并把每一处扣分的原因原样输出。得到的不只是一个分数，而是一份**可追溯的评分理由**。

## 2. 模型定义

| 维度 | key | 权重 | 观测内容 | 计分规则 |
|---|---|---|---|---|
| 流程完整度 | `flow` | 30 | 五个业务环节是否留痕 | `30 × 已完成环节数 / 应完成环节数` |
| 链上存证度 | `chain` | 30 | 批次与环节记录的存证覆盖 | 批次本体 15 分 + 环节上链率 × 15 分 |
| 质量合规性 | `quality` | 20 | 最近一次检测结论 | PASS 20 / FAIL 0 / 无报告 8 |
| 异常洁净度 | `abnormal` | 15 | 异常与数据更正记录 | 起始 15，处置中异常 −8/条，已处置 −3/条，更正 −2/次，下限 0 |
| 信息完备度 | `info` | 5 | 档案关键字段 | 农场、农户、产地、产量、采收日期各计 1 分（按比例折算到 5 分） |

总分 = 五维之和，钳制在 `[0, 100]`。

### 2.1 等级划分

| 分数 | 等级 | 文案 | 结论 |
|---|---|---|---|
| ≥ 85 | A | 高度可信 | 关键环节齐全、链上存证完整，可作为可信溯源凭证 |
| 70–84 | B | 基本可信 | 主体信息可信，个别环节记录或存证尚有欠缺 |
| 50–69 | C | 存疑 | 存在环节缺失或异常记录，建议向生产主体核实 |
| < 50 | D | 不可信 | 溯源档案严重不完整，不建议作为质量依据 |

## 3. 两个关键设计决策

### 3.1 阶段化：不能拿"还没发生"当"缺失"

一个还处在种植期的批次，没有采收、质检、物流记录是**正常的**。如果按五环节硬性要求，它会被判成 D 级"不可信"——这既不公平，也会让农户在批次刚建档时就看到一个刺眼的红标。

因此模型先根据批次当前状态推导"理应已经完成"的环节集合：

```
PLANTING              → [种植]
HARVESTED             → [种植, 采收]
QUALIFIED / ABNORMAL  → [种植, 采收, 质检]
IN_TRANSIT            → [种植, 采收, 质检, 物流]
ON_SALE / SOLD / CLOSED → [种植, 采收, 质检, 物流, 销售]
```

流程完整度、质量合规性、信息完备度（采收日期）三个维度都只在"该环节已进入"时才计分或扣分。批次走到哪、就考核到哪。

### 3.2 演示模式：环境问题不能算到批次头上

当 `chain.enabled=false`（链服务未部署）时，所有存证都会是 `SKIPPED`。若按真实规则计分，全部批次的链上维度都是 0 分，整个演示环境会被系统性压低 30 分。

模型对此的处理是：链上维度给固定的 **18/30**（60% 基础分），同时在 `deductions` 里明确写出「演示模式：链服务未启用，未做真实上链校验（-12）」。

这样既不会因为部署环境否定档案质量，也不粉饰——消费者能清楚看到"这一环没验到"。

## 4. 输出结构

```json
{
  "score": 88,
  "grade": "A",
  "gradeText": "高度可信",
  "summary": "关键环节齐全、链上存证完整，可作为可信溯源凭证",
  "dimensions": [
    { "key": "flow", "name": "流程完整度", "score": 30, "max": 30, "note": "5/5 个应完成环节" },
    { "key": "chain", "name": "链上存证度", "score": 18, "max": 30, "note": "演示模式未接入链服务" }
  ],
  "deductions": ["演示模式：链服务未启用，未做真实上链校验（-12）"]
}
```

`dimensions[].note` 与 `deductions[]` 都是**给人看的中文短句**，前端不需要再做任何映射，可以直接渲染。

## 5. 实测样本

| 批次 | 状态 | 分数 | 等级 | 主要扣分项 |
|---|---|---|---|---|
| AG20260512001 | SOLD | 88 | A | 演示模式未上链（-12） |
| AG20260518004 | SOLD | 88 | A | 演示模式未上链（-12） |
| AG20260515002 | ABNORMAL | 60 | C | 质检不合格（-20）、异常处置中（-8）、演示模式（-12） |
| AG20260601003 | PLANTING | 88 | A | 演示模式未上链（-12）；该阶段只需种植记录，故流程维度满分 |

异常批次与正常批次拉开了 28 分差距，且扣分项能直接对应到业务事实——这正是模型要达到的效果。

## 6. 工程特性

- **纯内存计算**：只读 `BatchDetailVO` 里已装配好的列表，不额外查库，单次评估为 O(n)，n 为记录条数（通常 < 20）。
- **零副作用**：不写库、不改状态，可以放心地在公开接口（消费者溯源）上调用。
- **无循环依赖**：`TrustScoreService` 只依赖 VO 与常量，被 `BatchService` 与 `TraceService` 单向引用。
- **复用**：批次详情（`BatchDetailVO.trust`）与扫码溯源（`TraceVO.trust`）用的是同一个方法，管理员与消费者看到的是同一套口径。

## 7. 与论文创新点的对应

| 常见写法 | 本项目的差异化 |
|---|---|
| "数据上链，保证不可篡改" | 不止判断是否上链，还量化**上链覆盖率**与**流程完整度** |
| "实现全流程溯源" | 用阶段化模型区分"尚未发生"与"确实缺失" |
| "消费者可查询溯源信息" | 消费者拿到的是一份**带扣分理由的可信度报告**，而不是一串原始记录 |
